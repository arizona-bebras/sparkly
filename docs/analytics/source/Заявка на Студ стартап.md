**Каким образом результат проекта решает проблему**

Опишите, как именно результат проекта может решить имеющуюся проблему (товара/изделия/технологии/услуги).

Наш продукт решает проблему следующим образом:

1. Получение данных: Встраиваемый агент сбора данных устанавливается в программу устройства, что позволяет собирать информацию о его работоспособности и получать журналы и метрики, которые передаются в облачную платформу.  
2. Автоматический анализ: Облачная платформа получает пакет данных с устройства через Интернет или иные каналы связи, сохраняет их в базу данных и проводит аналитику с помощью методов статистики и машинного обучения.  
3. Визуализация и статистика: Пользователь платформы видит состояние всего парка устройств, частые ошибки в них и дополнительную информацию, которая поможет улучшить работоспособность программной части устройства.  
4. Обновления: Пользователь может отправить обновление с исправлением на устройства, которое установится автоматически. Обновление распространяется на группы устройств последовательно с возможностью моментального отката на предыдущую версию в случае сбоя обновления.

Таким образом, пользователь получает сведения о проблемах и неполадках в реальном времени с удаленных устройств, сокращая время расследования инцидента на 30-60% и уменьшая общие затраты на диагностические выезды на 50-70%.

**Техническое решение проекта**

Опишите основную техническую идею, конструктивные особенности и т.д., положенные в основу создания продукта.

Техническое решение основано на создании высокопроизводительной экосистемы сбора телеметрии, использующей легковесные агенты для встраиваемых систем и событийно-ориентированную облачную архитектуру для анализа данных в реальном времени.

Архитектура: система представляет собой многоуровневую инфраструктуру, состоящую из  агентов, интегрированных непосредственно в прошивку микроконтроллеров, гибридной сети передачи данных (MQTT-брокер, шлюзы-посредники для протоколов BLE/USB) и облачной платформы для обработки входящих потоков данных, управления метаданными и координации устройств.

Технологии: языки программирования Rust и C++ (для написания энергоэффективных агентов и высоконагруженной серверной части), TypeScript (бизнес-логика и клиентская часть). Protocol Buffers для компактной упаковки данных, MQTT как основной протокол доставки, веб\-сокеты для обновления интерфейса в реальном времени. Базы данных InfluxDB (хранение временных рядов/метрик), PostgreSQL (хранение метаданных о пользователях, устройствах и иерархии парков). Фреймворки Svelte, Nest, Rocket.

Принцип работы:

1. Агент, встроенный в прошивку, собирает системные метрики (загрузка CPU, потребление памяти), логи приложения и состояние периферии. Данные преобразуются в бинарный формат Protobuf для минимизации трафика.  
2. Если устройство имеет прямой выход в сеть, данные уходят по MQTT. В случае отсутствия прямого соединения агент передает пакеты через доступный канал на промежуточный шлюз, который терминирует протокол и пересылает данные в облако.  
3. Облачный сервис декодирует Protobuf-пакеты. Метаданные (Номер устройства, права доступа) проверяются в PostgreSQL, а сами диагностические показатели записываются в InfluxDB.  
4. Сервер транслирует новые данные через веб\-сокеты в интерфейс на Svelte, обеспечивая мгновенное отображение графиков и статусов устройств без необходимости перезагрузки страницы пользователем.

# **Проблема:**

Продукт решает проблему «информационного вакуума» – устройства интернета вещей лишены инструментов «посмертной» диагностики, которые давно стали стандартом в веб\-разработке, что приводит к финансовым потерям из\-за простоев оборудования и низкого качества сервиса. Появление неполадок не может быть предсказано заранее, а поиск их первопричин и попытки воспроизвести сбой в отличных от полевых условиях являются сложными, а иногда невозможными.

До 75% провалов проектов интернета вещей связаны с проблемами на уровне устройств. Две трети компаний сообщают о регулярных проблемах подключения IoT‑устройств из‑за аппаратных причин; по данным [Eseye](https://info.eseye.com/2025-State-of-IoT-Report), отсутствие инструментов детальной диагностики полевых модулей напрямую выливается в простой систем и дополнительные расходы. Проблема нехватки внутренней информации с устройства для диагностики проблем с ним, приводит к финансовым потерям из\-за простоев оборудования и возможных юридических и репутационных рисков. 

Существующие процессы требуют физического доступа к поврежденному устройству (поиск причины неполадки, ремонт или замена), что в среднем занимает более суток, а также требует логистических затрат.

# **Техническое решение:**

Наш продукт решает проблему следующим образом:

1. Получение данных: Встраиваемый агент сбора данных устанавливается в программу устройства, что позволяет собирать информацию о его работоспособности и получать журналы и метрики, которые передаются в облачную платформу.  
2. Автоматический анализ: Облачная платформа получает пакет данных с устройства через Интернет или иные каналы связи, сохраняет их в базу данных и проводит аналитику с помощью методов статистики и машинного обучения.  
3. Визуализация и статистика: Пользователь платформы видит состояние всего парка устройств, частые ошибки в них и дополнительную информацию, которая поможет улучшить работоспособность программной части устройства.  
4. Обновления: Пользователь может отправить обновление с исправлением на устройства, которое установится автоматически. Обновление распространяется на группы устройств последовательно с возможностью моментального отката на предыдущую версию в случае сбоя обновления.

Таким образом, пользователь получает сведения о проблемах и неполадках в реальном времени с удаленных устройств, сокращая время расследования инцидента на 30-60% и уменьшая общие затраты на диагностические выезды на 50-70%.
