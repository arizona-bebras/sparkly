# Технический задел по репозиторию

Срез по рабочей копии на базе `8e94726`. Ниже описано то, что видно в коде, конфигурации и тестах. Это не целевая архитектура и не отчёт о запуске: тесты и стенд для этой сводки не запускались.

## Устройство и инструменты разработки

| Часть | Что есть | Границы |
| --- | --- | --- |
| [Агент на Rust](../../agent/README.md) | Переносимое ядро `no_std` без аллокатора, обычные логи и `defmt`, числовые метрики и события запуска. Пакеты Protobuf содержат идентификаторы сборки и сеанса работы; логи могут включать адреса кадров стека. Есть кольцевой RAM-буфер с учётом потерянных записей и повтор отправки ожидающего пакета. | RAM-буфер не переживает отключение питания. Захват аварийного дампа и постоянная очередь во флеше не реализованы. Повтор отправки не равнозначен серверной дедупликации. |
| [Пример на Linux](../../agent/examples/host/README.md), [адаптер Linux](../../agent/crates/sparkly-linux/) | Регистрация по токену парка и CSR, сохранение ключа и сертификата, отправка по HTTPS с mTLS. | Это пример на Linux, а не подтверждение передачи с микроконтроллера. Автоматического продления сертификата в примере нет. |
| [ESP32-S3](../../agent/crates/sparkly-esp/README.md) | Адаптер часов, причины сброса и захвата адресов стека; пример прошивки собирает логи и метрики и использует идентификатор сборки. | В примере транспорт намеренно офлайн. Встроенный сетевой транспорт и мосты BLE/USB не подтверждены реализацией в этом срезе. Ресурсные затраты и точность стека предстоит измерить на плате; поддержку других микроконтроллеров из заявки не считаем реализованной. |
| [CLI и сборка](../../agent/crates/sparkly-cli/README.md) | `sparkly init` настраивает интеграцию Rust-агента для ESP32-S3; `sparkly-link` встраивает идентификатор сборки после линковки; `sparkly inspect` проверяет ELF и извлекает метаданные. | CLI пока не загружает артефакты, не регистрирует устройства и не управляет ими; интеграция использует локальный SDK. |

## Серверные компоненты

| Часть | Что есть | Границы |
| --- | --- | --- |
| [Control Plane на Go](../../backend/cmd/backend/main.go) | API на ConnectRPC, PostgreSQL. Учёт пользователей, парков, групп и устройств; операции с записями инцидентов, сборок и релизов. Регистрация устройства по токену парка и CSR с выпуском сертификата через [step-ca](../../step-ca/README.md); сведения о группах передаются отдельным сообщением. | Записи сборок и релизов не означают доставку бинарников на устройство; операции с инцидентами не означают автоматическое создание инцидентов из телеметрии. |
| [Envoy и PKI](../../envoy/README.md) | Отдельные точки входа для пользовательского API, регистрации устройств и телеметрии. Пользовательские вызовы используют JWT, устройства предъявляют клиентский сертификат; шлюз передаёт аналитике подтверждённые идентификаторы устройства и парка. | Локальная конфигурация Compose предназначена для разработки, а не подтверждает готовность изолированного промышленного развёртывания. |
| [Analytics на Go](../../analytics/README.md) | Принимает бинарные Protobuf-пакеты по HTTP, передаёт их на обработку через RabbitMQ и сохраняет в ClickHouse сырые пакеты и расшифрованные события. Логи, метрики, загрузки и аварийные дампы хранятся в отдельных таблицах. Сведения о группах поступают по отдельному каналу. | Успешный ответ подтверждает публикацию в брокер. Представления ClickHouse устраняют дубли расшифрованных событий при чтении. [RPC чтения аналитики](../../analytics/cmd/analytics/main.go) пока не реализованы. |
| [Symbolicator на Rust](../../symbolicator/README.md) | Офлайн-декодер и отдельный worker RabbitMQ. По совпадающему идентификатору ELF расшифровывает `defmt`, имена метрик и адреса стека в функции и строки кода. Публикует результат в очередь. | Worker использует один локальный ELF. Интеграция с объектным хранилищем и группировка инцидентов остаются отдельными задачами. |
| [ML на Python](../../ml/src/sparkly_ml/main.py) | Каркас проекта и точка входа, пока без логики. | Предиктивной аналитики в текущем коде нет. |

## Интерфейс и проверка

- **Веб-интерфейс (SvelteKit/TypeScript).** [Клиенты ConnectRPC](../../frontend/proto/client.ts) и компоненты используют серверные вызовы для регистрации и входа, работы с парками и группами, просмотра устройств и работы с инцидентами. [Сводка по парку](../../frontend/src/routes/control-panel/%5Bpark_id%5D/+page.svelte) пока без данных. [Лента релизов](../../frontend/src/lib/components/entities/release/ReleaseTimeline.svelte) использует демонстрационные данные. Примеры подключения в настройках не заменяют актуальную инструкцию агента. Графики и журнал из [презентации](../../presentation/slides.md) — макеты, не подтверждение работающего просмотра телеметрии.
- **Локальная инфраструктура.** [Docker Compose](../../compose.yaml) описывает PostgreSQL, ClickHouse, RabbitMQ, Envoy, step-ca и профили приложений. Worker символикации запускается отдельно; он не включён в Compose.
- **Проверки.** В репозитории есть [CI](../../.github/workflows/ci.yml), тесты кодека, буфера и экспорта агента, шлюза и серверных компонентов; предусмотрены интеграционные проверки с ClickHouse и RabbitMQ. Наличие тестов не означает, что проверена сквозная работа на полевых устройствах.

## Что не следует выводить из этого среза

Сбор на ESP32-S3, защищённая передача из Linux-примера, сохранение сырых данных и расшифровка в отдельном worker — разные подтверждённые кодом части. Это не доказательство готового маршрута от микроконтроллера до журнала событий в интерфейсе. В частности, пока не связаны полевой транспорт, хранение и чтение результатов расшифровки, автоматическое открытие инцидентов и визуализация данных. Целевая архитектура и выбор будущих компонентов остаются отдельной задачей.
