# Sparkly — дизайн-документ презентации

## 1. Задача

Создать минималистичную, визуально выразительную презентацию проекта Sparkly на Slidev.

Sparkly — система централизованного мониторинга и телеметрии парка IoT-устройств. Она помогает видеть состояние контроллеров, собирать метрики и логи, фиксировать сбои и расследовать инциденты без обязательного выезда инженера.

Презентация должна передавать три качества продукта:

- Инженерная точность: понятные схемы, реальные сущности, чёткая иерархия.
- Наблюдаемость: превращение разрозненных сигналов устройств в понятную картину.
- Контроль: автономная инфраструктура, диагностика, управляемость парка.

Основной визуальный образ — искра полезного сигнала в тёмной технической среде.

Не создавать впечатление развлекательного приложения, криптопроекта или универсального AI-сервиса.

## 2. Утверждённое направление

Рабочее название стиля: «Тёмная телеметрия / Amber Signal».

Использовать первый согласованный брендборд с оранжево-янтарным акцентом как визуальный референс.

Основные характеристики:

- Глубокий графитовый фон.
- Тёмные поверхности карточек.
- Тонкие рамки и разделители.
- Оранжево-янтарный основной акцент.
- Голубой дополнительный цвет для потоков данных и графиков.
- Нейтральная светлая типографика.
- Моноширинные технические подписи.
- Много свободного пространства.
- Декоративная инженерная сетка только там, где она поддерживает композицию.

Не использовать лимонно-жёлтый акцент из второго варианта.

## 3. Логотип

Сохранить знак и написание Sparkly из первого согласованного изображения.

Правила:

- Не менять геометрию знака.
- Не заменять знак стандартной иконкой молнии.
- Не добавлять новые лучи, контуры, объём или градиенты.
- Основной цвет знака — `#F59E0B`.
- Название Sparkly — `#F1F5F9`.
- Логотип размещать преимущественно на титульном и финальном слайдах.
- На внутренних слайдах допустим небольшой знак в постоянной позиции, но не как обязательный водяной знак.

Если исходник логотипа доступен только в растровом брендборде, не придумывать другую форму. Запросить отдельный файл или аккуратно выделить существующий знак. Временный вариант — текстовое название Sparkly без нового символа.

## 4. Палитра

| Токен | Цвет | Назначение |
|---|---|---|
| `background` | `#0B0F14` | Основной фон |
| `surface` | `#131A22` | Карточки, панели, блоки схем |
| `border` | `#24303F` | Границы, разделители, сетка |
| `text` | `#F1F5F9` | Заголовки, основной текст |
| `muted` | `#94A3B8` | Подписи, пояснения, метаданные |
| `accent` | `#F59E0B` | Фирменный оранжево-янтарный акцент |
| `signal` | `#38BDF8` | Второй ряд графиков, транспорт данных |
| `success` | `#10B981` | Online, нормальная работа |
| `danger` | `#EF4444` | Ошибки, критические события |

### Правила применения

Основу слайда составляют фон и нейтральные поверхности. Акцентные цвета занимают небольшую часть композиции.

- Оранжевый — главный смысловой фокус.
- Голубой — дополнительный сигнал, а не конкурирующий главный акцент.
- Зелёный и красный — только статусные значения.
- Не раскрашивать каждую карточку отдельным цветом.
- Не использовать оранжевый для длинных абзацев.
- Не делать весь основной текст приглушённым.
- Для обычного текста сохранять светлый цвет `text`.

Полупрозрачная акцентная поверхность:

```css
background: rgba(245, 158, 11, 0.10);
border: 1px solid rgba(245, 158, 11, 0.30);
```

## 5. Типографика

Шрифтовая пара:

- `IBM Plex Sans` — заголовки, основной текст, пояснения.
- `JetBrains Mono` — числа, протоколы, идентификаторы устройств, логи, подписи метрик.

Использовать кириллические начертания.

| Элемент | Размер | Насыщенность |
|---|---:|---:|
| Название на обложке | 72–88 px | 600 |
| Крупный тезис | 48–60 px | 600 |
| Заголовок слайда | 36–44 px | 600 |
| Ключевая метрика | 56–72 px | 600 |
| Основной текст | 22–26 px | 400 |
| Текст карточек | 20–24 px | 400 |
| Подписи схем и графиков | 16–18 px | 400–500 |
| Второстепенные метаданные | 13–15 px | 400 |

Размеры заданы для холста `1280 × 720`. Если текст не помещается, сначала сокращать текст или менять композицию, а не уменьшать кегль.

Дополнительные правила:

- Заголовки преимущественно в одну-две строки.
- Не использовать сплошной uppercase для русскоязычных заголовков.
- Uppercase допустим в коротких технических бейджах: `ONLINE`, `MVP`, `INGRESS`.
- Моноширинный шрифт не применять ко всему слайду.
- Не использовать жирное начертание в каждом предложении.
- Избегать длинных центрированных абзацев.

## 6. Композиция

Формат: `16:9`.

Рабочий холст: `1280 × 720`.

Основная сетка:

- Горизонтальные поля: 64 px.
- Вертикальные поля: 48 px.
- Расстояние между крупными блоками: 32 px.
- Расстояние между карточками: 20–24 px.
- Внутренние отступы карточек: 24–32 px.
- Скругление карточек: 10–12 px.
- Толщина границ: 1 px.

Основной шаг отступов — 8 px.

### Принципы

Один слайд — одна мысль и один главный визуальный фокус.

На слайде предпочтительны:

- Один крупный тезис и его визуальное подтверждение.
- Две колонки: объяснение и схема.
- Три сопоставимых карточки.
- Одна крупная архитектурная схема.
- Один график с коротким выводом.

Не превращать каждый слайд в одинаковую сетку карточек. Чередовать текстовые, схемные и числовые композиции.

Внутри презентации сохранять постоянные позиции заголовков, служебных подписей и номера слайда.

## 7. Основные компоненты

### 7.1. Карточка

Тёмная поверхность, тонкая рамка, без тяжёлой тени.

Состав:

1. Небольшая техническая подпись или иконка.
2. Название.
3. Краткое пояснение.
4. При необходимости — значение или статус.

Не делать вложенные карточки без необходимости.

### 7.2. Статусный бейдж

Компактная плашка с маленькой точкой и коротким текстом.

Примеры:

- `ONLINE`
- `INCIDENT`
- `ON-PREMISES`
- `PROTOBUF`
- `MVP`

Бейджи не должны напоминать большие кнопки.

Статус обозначается не только цветом, но и текстом.

### 7.3. Метрика

Состав:

- Крупное число или диапазон.
- Короткое название показателя.
- Небольшое пояснение основания расчёта или статуса оценки.

Пример оформления:

```text
30–60%
целевое сокращение MTTR
гипотеза экономического эффекта
```

Не выдавать проектные ожидания за результаты измерений.

Диапазоны из описания проекта:

- Сокращение MTTR на 30–60%.
- Снижение затрат на выездную диагностику на 50–70%.

Пока нет подтверждённых результатов пилота, подписывать их как целевые показатели или гипотезы. Не подменять диапазоны максимальными значениями ради эффектного слайда.

### 7.4. Панель логов

Моноширинный текст на поверхности `surface`.

Пример демонстрационных данных:

```text
12:41:02  INFO   esp32-017  telemetry batch sent
12:41:08  WARN   esp32-017  supply voltage low
12:41:09  ERROR  esp32-017  unexpected reboot
```

Цветом выделять уровень сообщения, а не всю строку.

Количество строк — 3–6. Демонстрационные данные явно обозначать, если их можно принять за реальные.

### 7.5. Схемный узел

Карточка с названием компонента и короткой подписью роли.

Пример:

```text
Ingress
Приём и валидация Protobuf
```

Внутри одного уровня схемы узлы имеют одинаковые размеры и оформление.

## 8. Графики

График телеметрии должен содержать несколько линий.

Основная пара:

- Главная линия — `#F59E0B`.
- Вторая линия — `#38BDF8`.

Правила:

- Две линии — предпочтительный вариант.
- Третью добавлять только при смысловой необходимости.
- Линии должны показывать сопоставимые показатели на общей шкале.
- Не размещать напряжение и объём памяти на одной шкале без явного объяснения.
- Указывать единицы измерения и временную ось.
- Использовать тонкую малоконтрастную сетку.
- Добавлять короткую легенду или прямые подписи.
- Главная линия может быть немного толще второй.
- Не применять объём, свечение и тяжёлые градиентные заливки.

Рекомендуемый пример: температура двух устройств во времени.

```text
Заголовок: Температура устройств
Ось Y: °C
Ось X: время
Оранжевая линия: ESP32-017
Голубая линия: ESP32-024
```

Если данные синтетические, добавить подпись «Демонстрационные данные».

Событие перезагрузки можно обозначать вертикальным пунктиром и короткой подписью.

## 9. Архитектурные схемы

Визуально разделять:

1. Устройство и встроенный агент.
2. Приём телеметрии.
3. Хранилища.
4. Бизнес-логику.
5. Пользовательский интерфейс.

Отражать архитектуру проекта:

- Агент на Rust с C-совместимым FFI.
- Первичная платформа — ESP32.
- Передача телеметрии — Protobuf по защищённому каналу.
- Ingress — Go или Rust; окончательный выбор не изображать как уже сделанный.
- Логи — VictoriaLogs.
- Метрики — ClickHouse.
- Бизнес-логика — Go.
- Реестр устройств и связи — PostgreSQL.
- Внешний интерфейс сервиса — gRPC.

Правила изображения:

- Основной поток данных — слева направо.
- Разветвление логов и метрик показывать явно.
- Поток телеметрии — голубой.
- Регистрацию, ключевой этап или выбранный маршрут можно выделить оранжевым.
- Не соединять все узлы со всеми.
- Не рисовать прямые подключения устройств к аналитическим БД.
- Не придумывать промежуточные брокеры и сервисы, которых нет в согласованной архитектуре.

Для сложной схемы использовать два слайда: общий контур и отдельный процесс.

## 10. Декор и иконки

Допустимо:

- Очень слабая точечная сетка на обложке и разделителях.
- Тонкая акцентная линия.
- Маленькие статусные точки.
- Простые контурные иконки устройств, сети, базы данных и инцидентов.

Не использовать:

- Стоковые фотографии серверных.
- Изометрические 3D-объекты.
- Неоновые свечения.
- Фиолетово-синие AI-градиенты.
- Крупные декоративные молнии на каждом слайде.
- Эмодзи вместо иконок.
- Наборы иконок с разной толщиной линий.

Иконки должны помогать распознавать сущности, а не заполнять пустое пространство.

## 11. Набор макетов

| Макет | Композиция | Применение |
|---|---|---|
| Обложка | Логотип, крупное название, короткое описание | Первый слайд |
| Тезис | Один крупный вывод, минимум пояснений | Проблема или ключевая идея |
| Две колонки | Текст слева, схема справа | Объяснение решения |
| Три карточки | Три равнозначных блока | Аудитория, преимущества |
| Архитектура | Крупная схема на большей части слайда | Состав системы |
| Телеметрия | График и короткий вывод | Пример наблюдаемости |
| Метрики | Два-три крупных числовых блока | Экономический эффект |
| Сравнение | Две визуально сопоставимые области | MVP и дальнейшее развитие |
| Финал | Логотип, итоговый тезис | Завершение |

На обложке допустим крупный графический модуль телеметрии справа, но он не должен конкурировать с названием.

## 12. Рекомендуемый сценарий презентации

Базовый вариант — 10 слайдов.

| № | Тема | Визуальное решение |
|---:|---|---|
| 1 | Sparkly: мониторинг и телеметрия парка IoT | Обложка с логотипом |
| 2 | Устройства работают в поле, причины сбоев остаются неизвестными | Крупный тезис и три проявления проблемы |
| 3 | От сигналов устройства к расследованию инцидента | Последовательность из 4–5 этапов |
| 4 | Для кого создаётся продукт | Три карточки целевых ролей |
| 5 | Что входит в первый релиз | Основные функции и отдельная зона «Позже» |
| 6 | Как устроен Sparkly | Архитектурная схема |
| 7 | Что видит оператор | Схематичный интерфейс с графиком и логами |
| 8 | От критического события к инциденту | Короткая временная шкала |
| 9 | Ожидаемый экономический эффект | Диапазоны показателей с оговоркой |
| 10 | Контроль над парком без информационного вакуума | Финальный тезис и логотип |

Окончательный сценарий корректировать под аудиторию, не меняя дизайн-систему.

### Границы содержания MVP

В первый релиз включать:

- Метрики, текстовые логи и факты перезагрузок.
- Регистрацию устройства по токену группы.
- Приём и маршрутизацию телеметрии.
- Просмотр устройств, групп, логов и графиков.
- Статусы доступности.
- Фиксацию критических ошибок как инцидентов.

Отдельно обозначать как дальнейшее развитие:

- OTA и безопасный откат.
- Coredump и слепки RAM.
- Разбор debug symbols.
- Двустороннее командное управление.
- Расширенную ролевую модель.
- Предиктивную аналитику.

Не изображать функции следующего этапа как готовые возможности MVP.

## 13. Реализация на Slidev

Базовая тема — `apple-basic`. Итоговые стили должны соответствовать этому документу, а не стандартному виду темы.

Стартовая конфигурация:

```yaml
---
theme: apple-basic
title: Sparkly
colorSchema: dark
aspectRatio: 16/9
canvasWidth: 1280
fonts:
  sans: IBM Plex Sans
  mono: JetBrains Mono
  weights: '400,500,600,700'
transition: fade-out
---
```

Организация проекта:

```text
slides.md
style.css
components/
  StatusBadge.vue
  MetricBlock.vue
  TelemetryChart.vue
  LogPanel.vue
public/
  logo.svg
  fonts/
```

Slidev автоматически подключает Vue-компоненты из `components/`. Небольшие декоративные элементы можно оставить в `slides.md`.

### Графика и автономность

- Логотип и схемы — предпочтительно SVG.
- Простой график — SVG или небольшой Vue-компонент.
- Не добавлять тяжёлую библиотеку ради двух линий.
- Избегать внешних изображений и виджетов, загружаемых во время показа.
- Для автономного показа хранить шрифты и прочие ресурсы локально.
- Презентация должна оставаться понятной при экспорте в статичный PDF.

## 14. Анимации

Анимация поддерживает рассказ, а не демонстрирует возможности фреймворка.

Разрешено:

- Мягкое появление.
- Последовательное раскрытие этапов.
- Поэтапная подсветка архитектурного маршрута.

Не использовать:

- Постоянное пульсирование.
- Автоматически бегущие линии.
- Вращение и масштабирование карточек.
- Печатание длинного текста.
- Декоративные переходы между каждым слайдом.

Не скрывать важные сведения так, чтобы они пропадали в PDF.

## 15. Редакционные правила

Тон — спокойный, технический, конкретный.

Предпочитать формулировки:

- «Собирает метрики и логи».
- «Фиксирует внеплановые перезагрузки».
- «Помогает расследовать инциденты».
- «Работает в изолированном контуре».

Избегать:

- «Революционная платформа».
- «Полный контроль над всем».
- «Гарантированно сокращает затраты».
- «Автоматически соответствует 152-ФЗ».

Возможность on-premises-развёртывания не представлять как самостоятельное доказательство соответствия законодательству. Бейдж `152-ФЗ` использовать только с корректным пояснением и основанием; при их отсутствии заменить на `ИЗОЛИРОВАННЫЙ КОНТУР`.
